# План реализации: ЛР1 «Стоматология — запись на приём»

## 1. Результат

Монолитное REST-приложение на Java 21 и Spring Boot, которое позволяет управлять пользователями, каталогом стоматологических процедур и записями пациентов к врачам. Данные хранятся в PostgreSQL, схема создаётся Liquibase, приложение и БД запускаются через Docker Compose. API документируется OpenAPI/Swagger и покрывается модульными и интеграционными тестами не менее чем на 70%.

## 2. Зафиксированные ограничения

- Ровно четыре JPA-сущности: `User`, `Appointment`, `DentalProcedure`, `AppointmentProcedure`.
- `User` представляет пациента, врача, администратора или директора; роль хранится строковым enum.
- Spring Security и JWT не входят в ЛР1.
- Telegram и брокеры сообщений не входят в ЛР1; уведомление выполняется внутренним сервисом без отдельной сущности.
- Отдельного `TimeSlot` нет: свободное время вычисляется по рабочему интервалу и существующим записям.
- Все списочные endpoint-ы ограничены 50 элементами.

Дополнительные join-таблицы не считаются сущностями: `doctor_procedures` реализует обычную M:N, а `user_specializations` хранит набор строковых enum-значений врача.

## 3. Предметная модель

### User

- `id`, `fullName`, `phone`, `email`, `role`, `active`;
- для врача: набор `specializations`, начало и конец рабочего дня;
- M:N с `DentalProcedure`: процедуры, которые врач выполняет.

### Appointment

- `id`, `patient`, `doctor`, `startsAt`, `endsAt`, `status`, `comment`, `createdAt`, `updatedAt`;
- две связи M:1 с `User`: пациент и врач;
- 1:N с `AppointmentProcedure`.

### DentalProcedure

- `id`, `name`, `description`, `basePrice`, `durationMinutes`, `active`;
- M:N с врачами;
- 1:N с `AppointmentProcedure`.

### AppointmentProcedure

- `id`, `appointment`, `procedure`, `price`, `quantity`, `toothNumber`;
- является связью M:N с дополнительными полями;
- `price` сохраняется как цена на момент приёма и не изменяется вместе с каталогом.

## 4. Архитектура

Один Spring Boot-модуль с разделением по предметным пакетам:

```text
user/                 User: controller, service, repository, DTO
procedure/            DentalProcedure и доступные врачу процедуры
appointment/          Appointment и AppointmentProcedure
notification/         интерфейс и локальная реализация уведомлений
common/               ошибки, обработчик исключений, пагинация
config/               OpenAPI и конфигурация приложения
```

Entity не возвращаются из контроллеров напрямую: для запросов и ответов используются отдельные DTO.

## 5. REST API

### Пользователи

- `POST /api/v1/users`
- `GET /api/v1/users/{id}`
- `GET /api/v1/users?page=&size=&role=`
- `PUT /api/v1/users/{id}`
- `DELETE /api/v1/users/{id}` — мягкое отключение пользователя
- `PUT /api/v1/users/{doctorId}/procedures/{procedureId}`
- `DELETE /api/v1/users/{doctorId}/procedures/{procedureId}`
- `GET /api/v1/users/{doctorId}/availability?date=`

### Каталог процедур

- `POST /api/v1/procedures`
- `GET /api/v1/procedures/{id}`
- `GET /api/v1/procedures?page=&size=` — общее количество в `X-Total-Count`
- `PUT /api/v1/procedures/{id}`
- `DELETE /api/v1/procedures/{id}` — мягкое отключение процедуры

### Записи

- `POST /api/v1/appointments`
- `GET /api/v1/appointments/{id}`
- `GET /api/v1/appointments?cursor=&size=` — бесконечная прокрутка без общего количества
- `PATCH /api/v1/appointments/{id}/reschedule`
- `PATCH /api/v1/appointments/{id}/complete`
- `DELETE /api/v1/appointments/{id}` — отмена записи
- `POST /api/v1/appointments/{id}/procedures`
- `PUT /api/v1/appointments/{id}/procedures/{itemId}`
- `DELETE /api/v1/appointments/{id}/procedures/{itemId}`

## 6. Бизнес-правила

- В `Appointment.patient` разрешён только активный пользователь с ролью `PATIENT`.
- В `Appointment.doctor` разрешён только активный пользователь с ролью `DOCTOR`.
- Начало приёма раньше окончания и находится внутри рабочего времени врача.
- У одного врача не может быть пересекающихся активных записей.
- Пациент также не может иметь две пересекающиеся активные записи.
- Выполненную или отменённую запись нельзя переносить.
- Процедуры можно добавлять только врачу, который их выполняет.
- `quantity` положительное, `price` неотрицательная, `toothNumber` при наличии находится в диапазоне 1–32.
- Все enum сохраняются в БД как строки.

## 7. Транзакционные операции

### Создание записи

1. Заблокировать строку врача (`PESSIMISTIC_WRITE`).
2. Проверить роли, активность, рабочее время и пересечения.
3. Создать запись.
4. Вызвать внутренний сервис уведомлений после успешного изменения.

Блокировка врача сериализует конкурирующие попытки записи к одному врачу и предотвращает двойное бронирование.

### Перенос записи

1. Заблокировать врача и текущую запись.
2. Проверить статус записи и доступность нового интервала.
3. Обновить время записи.
4. Вызвать внутренний сервис уведомлений.

Если любая проверка завершается ошибкой, прежнее время записи остаётся без изменений.

## 10. Риски

| Риск | Решение |
|---|---|
| Одновременная запись к одному врачу | Пессимистическая блокировка врача внутри транзакции и интеграционный тест конкуренции |
| Ровно четыре Entity, но больше четырёх таблиц | Явно документировать, что join-таблицы и enum-коллекция не являются Entity |
| Цена процедуры меняется после приёма | Хранить цену-снимок в `AppointmentProcedure` |
| Уведомление происходит до commit | Локальную отправку вызывать после успешного изменения; внешнюю доставку оставить для ЛР4 |
